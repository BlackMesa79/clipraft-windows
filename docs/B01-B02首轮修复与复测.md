## B-02：校正残留的触发键按下状态

六次分析中B-02三组失败明确满足ready/配置门/修饰键条件，但V缓存为按下，`repeated=true`阻止Open。原状态机只校正修饰键缓存，不能恢复未被有效释放的普通触发键状态。

本次在**另一真实修饰键事件**到达时采样当前配置触发键的GetAsyncKeyState。只有以下条件同时满足才清除旧触发键缓存：

- quick非活动、未录制；采样键与状态机当前配置触发键相同。
- 系统采样显示该触发键已松开，内部缓存却仍按下。
- 该触发键没有待配对的已吞按下。

不在触发键事件本身用异步状态判断它是否刚按下（低级钩子时该状态仍可能是前事件状态）；注入事件不采样/校正，不从系统状态凭空创建真实按下。active或已吞键仍由原长按/配对释放规则处理，不简单移除 `!repeated`。

新的 `trigger_reconciled source=modifier_sample cached_down=true system_down=false` 表示本轮校正确实发生；仍使用定长消息投递到诊断线程，不在钩子中格式化字符串或写文件。

隔离回放比较同一前序序列：Alt+V按下、真实V-up缺席、Alt释放、Ctrl+Shift+V。未校正分支明确无Open，加入校正后首次按下Open。另验证系统仍按下、配置键不匹配、活动会话、Esc后待配对按键都不被误清除，既有长按/录制/吞键测试继续通过。真实释放为何在某些前序操作中未有效进入状态机仍未归因到应用或IME，本修复针对已证实的缓存阻断。

## B-01：恢复呼出前的输入子窗口并等待焦点稳定

日志三次主窗粘贴都在Codeg宿主→WebView2焦点交接附近注入，两次注入前仍是宿主，一次仅刚切入。因此仅等待顶层foreground匹配不足，但也不能只检测到某个Chromium类名就认为IME已就绪。

本次主面板显示前只读保存目标输入焦点的 HWND/PID/TID 及所属顶层窗口。粘贴仍使用原有SetForegroundWindow恢复目标，随后：

1. 只有主面板restore=true且成功捕获原输入子窗口时启用新检查。quick的restore=false路径保持。
2. 每5ms只读采样，要求回到呼出前的同一有效输入子窗口并连续稳定30ms；中间变化重新计时，判定上限300ms。
3. 目标变成其他前台窗口、原输入窗口失效/身份改变时取消；新粘贴代号到来立即按原过期语义停止。超时提示原输入框焦点未恢复。
4. SendInput前再次核对目标子焦点及代号，避免准备阶段之后又变化而误贴。

没有新增SetFocus、AttachThreadInput、修饰键补发、窗口类名硬编码或IME正文读取。未捕获到可靠输入子窗口时保留原准备行为，诊断 `paste_focus captured=false` 明确标记；没有把未知子窗口强行指定为目标。

**30ms是连续状态稳定窗口，不是无条件睡眠；仍不能证明IME内部状态已经完全就绪。** 真实Codeg表现需要用户复测。若仍失败，后续根据focus_restore与focus_probe判断是否需进一步定位目标消息/IME层，不能无依据持续加长延时。

新增诊断：`focus_restore captured`（呼出前身份）、`paste_focus captured`、`focus_restore generation=... elapsed_ms=... result=ready/superseded/cancelled`。此前定向日志仍保留，不记录窗口正文、标题或剪贴板内容。

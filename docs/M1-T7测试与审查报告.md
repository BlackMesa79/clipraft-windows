### P2-1：紧贴中文的样例不符合本次识别要求（已修复）

- 位置：`src-tauri/src/sensitive.rs:10`、`:13`，以及检测循环的左边界检查。
- 条件：将明显为假的 `sk-TESTONLY0000000000000000abcd` 紧贴中文，例如 `中文sk-TESTONLY0000000000000000abcd` 或在其后紧接中文。
- 修复前：本次规格要求命中，但 `word()` 使用 `char::is_alphanumeric()`，把汉字视为单词的一部分，左右边界会排除该样例。
- 修复前影响：此类输入不会进入自动敏感标记、搜索排除和到期删除流程。周围有标点或空白时的识别不受这一差异影响。
- 验收测试：`src-tauri/tests/sensitive_rules.rs` 的 `chinese_adjacent_tokens_meet_requested_acceptance_rule`，已移除 ignore 并通过；覆盖中文两侧、全角字符、标点、UTF-8 精确区间和脱敏上下文。
- 修复结果：`word()` 改为 ASCII 字母数字、`_`、`-`，其他字符均为边界。README 已同步；`task-…`、`risk-…` 等内嵌反例及定长规则的 ASCII 右边界断言保留通过。

### P2-2：JWT 头被额外限定为 `eyJ` 开头（已修复）

- 位置：`src-tauri/src/sensitive.rs` 的 JWT 候选识别与 `json_object()`。
- 条件：三个有效 base64url 段，头部解码为 `{ "alg":"HS256" }`。该 JSON 含合法空白，编码不以 `eyJ` 开头。
- 修复前：本次规格只要求头部为含 `alg` 的 JSON，但实现还先检查 `rest.starts_with("eyJ")`，因此不会进入 JSON 校验。
- 修复前影响：上述合法 JSON 头的 JWT 形状内容不会被自动标记。常见无空白头的既有测试仍通过。
- 验收测试：`src-tauri/tests/sensitive_rules.rs` 的 `jwt_json_header_with_whitespace_is_accepted`，已移除 ignore 并通过。保留原样例，新增 JSON 前导空格、Tab、CR、LF、混合空白及 payload 前导空白，检查中文上下文中的精确区间。
- 修复结果：不再限定 `eyJ`，用合法对象起始字节对应的 base64url 首字符 `e/I/C/D` 预筛。头部解码后跳过前导空白须以 `{` 起始，解析为含 `alg` 的 JSON 对象；payload 同样必须为 JSON 对象；签名保留非空、无 padding、合法 base64url 解码检查。遇到第三个点立即排除多段候选，避免扩大预筛后重复扫描过长候选；失败候选不吞掉后续独立 token。

以上两项在 Tester 初轮审查中记录为待修；本次均已修复并启用验收测试，规则集成测试为 16 passed / 0 failed / 0 ignored。这不构成对未覆盖平台交互的通过声明。

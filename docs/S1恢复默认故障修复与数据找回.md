# S1 恢复默认故障修复与数据找回

日期：2026-11-15。状态：代码修复及自动/隔离原生验证完成；旧历史已找回并独立保留，未覆盖当前数据。尚未重新打包、提交或推送，用户正在运行的旧 release 程序未被替换。S1 重新进入复验，K1/U4 暂不推进。

## 1. 原因与证据

此前启动定位 `startup.json` 和默认数据根目录共处 `%APPDATA%/ClipboardM0`。用户为恢复默认而清理这个目录时，会同时删除指向自定义数据位置的启动定位。

运行中的应用仍持有自定义数据目录；再次读取缺失的定位文件时，旧实现返回默认目录。提交迁移时根目录比较不一致，因此弹出“启动定位已改变，请重新启动后再迁移”，此错误发生在写入待迁移任务之前，实际没有提交迁移。设置页“保存”只保存普通设置，不会补回启动定位。

随后重启再次把缺失配置视为首次启动，回到默认位置初始化新库，造成历史消失。`webview` 无法删除是缓存仍被当前进程使用；它既不包含 SQLCipher 历史库，也不能替代启动定位。

这是实现和恢复默认操作引导的缺陷。旧文档要求用户处理默认位置残留副本、却把启动配置放在同一目录，而且错误提示建议重启；原自动回归没有覆盖清理默认目录同时删除定位文件的实际路径。

证据包括：截图对应 `commands::schedule` 错误分支、`Configuration::load` 缺文件回退行为、回收站中指向自定义目录的旧 `startup.json`，以及本轮配置缺失和返回默认目录的重现测试。

## 2. 已修复

- 正常安装模式的定位配置迁到 `%APPDATA%/ClipRaft/startup.json`，与默认历史目录 `%APPDATA%/ClipboardM0` 分离。旧定位仍存在时兼容读取，成功打开现有库后持久化到独立配置位置；持有旧配置锁防止升级时并行运行旧实例。WebView 保持原缓存位置以免破坏已有用户缓存。
- 首次成功打开数据库后也保存定位，并写入独立 `initialized` 标记。已初始化却缺少定位文件时停止自动回退，通过恢复入口选择现有数据；已检查存在但读取时消失同样报错，不能再返回默认空库。
- 旧版本只剩 WebView 缓存、数据库/密钥和定位均丢失的情况不视作全新安装，也进入恢复错误流程。
- 运行时配置不一致在预检及确认时都阻止；提示保留当前目录，不再建议直接重启造成空库。
- 恢复默认允许默认位置有旧的应用管理数据。确认页提前显示独立旧数据保留位置；冷迁移先把目标旧数据移到默认目录的同级 `ClipRaft-preserved-<随机标识>`，保留配置、锁、WebView 和诊断资源，再迁入当前数据。不会合并或删除旧历史，也无需手工清空。
- 旧数据保留过程有清单和完成标记。移动一半、保留完成但新内容复制中断均可续做；不会在重试时把刚复制的新数据再次归档。越界保留路径、未知用户文件和冲突文件会阻止操作。
- 普通的非空自定义目标仍拒绝；数据存储页展示最近一次迁移源副本，以及恢复默认时保留的目标旧数据。

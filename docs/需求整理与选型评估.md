# 剪贴板管理器：需求整理与技术选型评估

> 日期：2026-11-09
> 参考对象：Ditto、CopyQ、Clippi（Rust + GPUI）
> 目标平台：先做 Windows（你现在用的是 Win11，Ditto 也只支持 Windows），架构上为 macOS 留扩展余地

---

## 一、现有软件的痛点整理

| 软件 | 优点 | 问题 |
|---|---|---|
| **Ditto** | 功能最符合需求：分组、快速粘贴、多格式保存、纯文本粘贴、网络同步 | 技术老（MFC），界面过时，基本没有现代化的视觉设计 |
| **CopyQ** | 综合能力强：多标签页（分组）、备注/标签、命令与脚本、命令行、忽略指定窗口/内容、可定制外观 | **复制文件产生的记录无法作为文件重新粘贴**（只保存了路径文本/URI，没有还原成 Windows 的文件剪贴板格式） |
| **Clippi** | 界面最好看，功能点也多：拼音搜索、OCR、二维码、同步、脱敏、表情面板 | ① 呼出面板时**偶尔导致系统输入卡死**；② **部分图片没有预览**；③ **没有分组**；④ **没有"按住快捷键 + 方向键选择 + 松开即粘贴"的快速粘贴面板**；⑤ bug 多 |

### 痛点对应的技术根因（设计时必须规避）

1. **输入卡死**：Windows 下最常见的原因有三个：
   - 全局低级键盘钩子（`WH_KEYBOARD_LL`）的回调里做了耗时操作，或者挂钩子的线程消息循环被 UI 渲染阻塞。系统会等待钩子回调（`LowLevelHooksTimeout`，约 300ms～1s），期间整机键盘输入都会卡住，超时多次后钩子会被系统静默移除。
   - 抢焦点逻辑出错：用 `AttachThreadInput` 把线程输入队列和目标窗口挂在一起后没有解除，导致两边的输入状态互相锁住。
   - 模拟按键（`SendInput`）时修饰键状态没有还原，比如 Alt/Ctrl 处于"逻辑按下"状态，看上去就像打不了字。
   - **对策**：钩子放在独立线程，只有自己的消息循环，回调里只投递消息、立刻返回；面板用不获取焦点的窗口（`WS_EX_NOACTIVATE`）；模拟粘贴前后严格校验并恢复修饰键状态。
2. **文件不能粘贴**：文件复制在 Windows 里是 `CF_HDROP` 格式，同时带有 `Preferred DropEffect`（复制/剪切）。**对策**：记录文件时保存路径列表和 DropEffect，粘贴时重新构造 `CF_HDROP`，资源管理器、微信、QQ、聊天软件、IDE 里都可以直接粘贴成文件；源文件被删除时在列表里标记"文件已失效"。
3. **图片无预览**：图片在剪贴板里可能是 `CF_DIB` / `CF_DIBV5`（带透明通道）、`PNG` 注册格式、`CF_HDROP`（复制的图片文件）、`HTML Format` 里的 `<img>`（浏览器复制），有时还是 WebP/HEIC/SVG。只认其中一种就会出现部分图片没有预览。**对策**：按优先级读取多种格式，统一生成缩略图缓存；无法解码时显示格式名 + 尺寸占位，而不是空白。

## 三、快速粘贴面板交互设计（P0 核心）

这是 Clippi 缺失、你最在意的功能，单独说明：

1. **触发**：按住修饰键组合（默认如 `Ctrl+Shift`），再按一次触发键（如 `V`）时呼出小面板，此时默认选中**第 2 条**（第 1 条就是当前剪贴板，和 Alt+Tab 的逻辑一样）。
2. **选择**：在修饰键保持按下的情况下：
   - 再按 `V` 或 `↓` 选下一条，`↑` 或 `Shift+V` 选上一条；
   - `←` / `→` 切换分组（可选）；
   - 鼠标滚轮也可以选择。
3. **确认**：松开修饰键后，把选中记录写回剪贴板，并向原窗口模拟 `Ctrl+V`。
4. **取消**：按 `Esc`，或者选中"取消"项后松开。
5. **位置**：优先显示在文本光标附近（`GetGUIThreadInfo` / UI Automation 获取光标位置），获取不到时显示在鼠标附近。
6. **关键实现约束**：
   - 面板窗口为 `WS_EX_NOACTIVATE | WS_EX_TOPMOST | WS_EX_TOOLWINDOW`，**永远不获取焦点**，原窗口的输入法和焦点保持不变；
   - 按键识别完全由独立线程上的低级键盘钩子完成，并且**拦截**掉面板期间的方向键，不让它传到目标程序；
   - 如果修饰键包含 Alt 或 Win，单独松开会触发菜单栏或开始菜单，需要在松开前注入一个无意义的虚拟按键来抑制；
   - 面板窗口预先创建并隐藏，呼出时只做显示，保证延迟在一帧（约 16ms）以内。

## 四、技术选型评估

### 关键技术难点（任何方案都绕不开）

剪贴板监听、多格式读写、`CF_HDROP` 构造、低级键盘钩子、不抢焦点窗口、模拟按键、获取文本光标位置——**这些全都是 Win32 API 层面的工作**。所以选型的核心问题是：
**① 调用 Win32 API 是否顺手；② 能否轻松做出好看的界面；③ 常驻后台的内存占用和启动速度。**

### 候选方案对比

| 方案 | Win32 交互 | 界面美观度/开发效率 | 内存占用（常驻） | 跨平台 | 成熟度/风险 | 评价 |
|---|---|---|---|---|---|---|
| **A. Tauri 2（Rust 核心 + WebView2 前端 Vue/React/Svelte）** | ★★★★★ 通过 `windows-rs` 官方绑定直接调用 | ★★★★★ 前端生态，动画和样式随意 | 中（约 60～120MB，WebView2 占大头） | Win/Mac/Linux | 成熟、社区大 | **推荐** |
| B. C# .NET 8+ WPF（配合 WPF-UI 等 Fluent 风格库） | ★★★★☆ P/Invoke 方便，资料极多 | ★★★★☆ 能做出 Win11 风格，但复杂动画不如 Web 灵活 | 中（约 50～100MB） | 仅 Windows（若需跨平台要换 Avalonia） | 非常成熟 | 如果你更熟悉 C#，这是最稳的方案 |
| C. C# + WinUI 3 | ★★★☆☆ | ★★★★★ 原生 Win11 外观 | 中 | 仅 Windows | 不抢焦点窗口、窗口样式定制在 WinUI 3 中坑较多，打包部署繁琐 | 不推荐 |
| D. Rust + GPUI（Clippi 的方案） | ★★★★★ | ★★★☆☆ 组件少、文档少 | 低 | Win/Mac | GPUI 为 Zed 编辑器服务，Windows 端较新，API 不稳定 | 不推荐，Clippi 的问题部分与此相关 |
| E. Rust + Slint / iced / egui | ★★★★★ | ★★☆～★★★☆ | 低（10～30MB） | 全平台 | 中等 | 想要极致轻量可以考虑，但做漂亮界面成本高 |
| F. C++ + Qt/QML（CopyQ 的方案） | ★★★★☆ | ★★★★☆（QML） | 低～中 | 全平台 | 成熟 | 开发和构建成本高，不如 A 高效 |
| G. Electron | ★★☆☆☆ 原生调用要写 Node 原生模块 | ★★★★★ | 高（150MB+） | 全平台 | 成熟 | 剪贴板工具常驻后台，太重，不推荐 |

### 推荐方案：Tauri 2 + Rust 核心

```
┌──────────────────── 前端（WebView2）────────────────────┐
│  主窗口：Vue 3 / Svelte + 虚拟列表 + 预览面板           │
│  快速面板：独立的轻量页面，预先加载并隐藏               │
└───────────────▲──────────────────────┬──────────────────┘
                │ 事件推送              │ 命令调用（invoke）
┌───────────────┴──────────────────────▼──────────────────┐
│ Rust 核心                                                │
│  ├─ clipboard  ：格式监听/读取/写回（含 CF_HDROP、DIBV5、│
│  │               HTML、RTF、PNG），windows-rs           │
│  ├─ hook       ：独立线程的低级键盘钩子 + 状态机         │
│  ├─ paster     ：焦点记录与恢复、SendInput、修饰键还原   │
│  ├─ storage    ：SQLite（rusqlite）+ FTS5 全文检索       │
│  │               + 拼音索引列；大对象以文件形式存放      │
│  ├─ thumbnail  ：image crate 生成缩略图（后台线程）     │
│  └─ platform   ：平台抽象层（以后接入 macOS 实现）       │
└──────────────────────────────────────────────────────────┘
```

**推荐理由：**
1. 所有 Win32 难点都在 Rust 层用 `windows-rs` 直接处理，没有中间层限制；
2. 界面用 Web 技术，想做到比 Clippi 更好看也很容易，主题、动画、虚拟列表都有现成方案；
3. Rust 核心稳定性好，长期常驻后台不容易出现内存泄漏或崩溃；
4. 以后想支持 macOS，只需要重新实现 `platform` 层，界面和存储都可以复用。

**需要注意的地方：**
- 快速面板窗口要在 Rust 侧设置 `WS_EX_NOACTIVATE`，键盘事件全部来自钩子，由 Rust 推送选中状态给前端，**前端页面本身不接收键盘输入**；
- WebView2 首次创建较慢（几百毫秒），所以两个窗口都要在启动时预先创建并隐藏；
- 列表数据只把当前页和缩略图路径传给前端，不要把图片原始数据通过 IPC 传过去。

**备选**：如果你对 C# 比对 Rust 熟悉很多，选 **方案 B（.NET 8 + WPF）**，Win32 交互同样顺手，开发速度可能更快，代价是放弃跨平台。

### 存储设计要点
- SQLite 一个库：`items`（元数据、哈希、来源程序、时间、分组、置顶）、`item_formats`（每种格式一行，小数据内联，大数据存文件路径）、`groups`、`tags`；
- 搜索：FTS5 + 预先计算的拼音全拼/首字母列；
- 图片原图存放于 `data/blobs/`，按哈希命名，天然去重。

### 已确定的决策（2026-11-09）
- 技术栈：Tauri 2 + Rust 核心，第一阶段只做 Windows。
- 本地数据必须加密（剪贴板里经常有密码、API token）。

### 数据加密方案

**1. 数据库整库加密：SQLCipher**
- `rusqlite` 开启 `bundled-sqlcipher-vendored-openssl` 特性，整个数据库文件（包括 FTS 索引）用 AES-256 加密，对上层 SQL 透明，性能损耗通常在 5%～15%。

**2. 密钥管理：Windows DPAPI（默认）+ 可选主密码**
- 首次启动随机生成 32 字节主密钥，用 `CryptProtectData` 加密后存到 `%APPDATA%`。用户登录 Windows 后自动解密，**不用每次输入密码**。
- 数据库文件被拷到别的电脑或别的 Windows 账户都无法解密。
- 可选"主密码"模式：用 Argon2id 从主密码派生密钥，启动或解锁时需要输入，适合对安全要求更高的场景。

**3. 数据库之外的文件也要加密**
- `data/blobs/` 里的原图、文件快照、缩略图用 XChaCha20-Poly1305 逐个加密（`chacha20poly1305` crate），密钥从主密钥派生。
- 缩略图只在内存里解密，通过 Tauri 自定义协议提供给前端，不落地明文临时文件。
- 日志里不记录剪贴板内容。

**4. 少记录才是最有效的保护**
- 遵守系统约定的标记：剪贴板里出现 `ExcludeClipboardContentFromMonitorProcessing`，或 `CanIncludeInClipboardHistory = 0` 时**直接不记录**。1Password、Bitwarden、KeePass 等密码管理器复制密码时都会设置这些标记。
- 忽略程序列表默认包含常见密码管理器。
- 敏感内容识别：用规则匹配 `sk-…`、`ghp_…`、`AKIA…`、JWT、私钥头等格式，命中后标记为"敏感"：列表中脱敏显示，N 分钟后自动删除（可配置），不参与同步。
- 删除记录时同时删除 blob 文件，并定期执行 `VACUUM`，减少残留。

**5. 能防什么、不能防什么**
- 能防：硬盘或数据目录被拷走、备份泄露、其他 Windows 账户读取。
- 不能防：以当前用户身份运行的恶意程序（它本来就能直接读剪贴板）。如果担心这种情况，需要开启主密码模式并设置自动锁定。

## 五、建议的开发阶段

| 阶段 | 内容 |
|---|---|
| **M0 技术验证（最先做）** | 1) 低级键盘钩子 + 不抢焦点面板 + 松开粘贴，在记事本、浏览器、微信、VS Code、管理员终端里验证不卡输入、不影响输入法；2) `CF_HDROP` 文件写回在资源管理器和聊天软件中可粘贴；3) 各种来源图片的读取与缩略图；4) SQLCipher + DPAPI 加密存储能正常打开和读写 |
| M1 MVP | 全部 P0：监听与存储、主窗口、搜索、分组、置顶、快速面板、纯文本粘贴、托盘、自启、忽略规则 |
| M2 | P1：拼音搜索、标签备注、编辑、拖拽、OCR、主题、备份、管理员模式、数字键粘贴 |
| M3 | P2：同步、文本转换、顺序粘贴、二维码、macOS 移植 |

M0 的三个验证点正好对应三款软件的三个核心缺陷，先把它们做通再搭界面，可以避免后期返工。

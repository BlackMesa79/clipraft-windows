# M1 / T1–T2 存储层说明

更新日期：2026-11-10。当前 `PRAGMA user_version = 3`。

## 最终 schema

以下是版本 3 的等价建表语句。实现采用事务内创建 v0 表后逐版迁移，新库与 M0 旧库升级后的 schema 已通过一致性测试。

```sql
CREATE TABLE groups (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    sort INTEGER NOT NULL,
    created INTEGER NOT NULL
);
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
CREATE TABLE items (
    id TEXT PRIMARY KEY,
    view TEXT NOT NULL,
    touched INTEGER NOT NULL,
    kind TEXT NOT NULL DEFAULT 'text',
    created INTEGER NOT NULL DEFAULT 0,
    used_at INTEGER NOT NULL DEFAULT 0,
    size INTEGER NOT NULL DEFAULT 0,
    pinned INTEGER NOT NULL DEFAULT 0,
    favorite INTEGER NOT NULL DEFAULT 0,
    group_id INTEGER REFERENCES groups(id),
    source_exe TEXT,
    source_title TEXT,
    sensitive INTEGER NOT NULL DEFAULT 0,
    expires_at INTEGER,
    search_text TEXT NOT NULL DEFAULT '',
    thumbnail TEXT,
    preview TEXT,
    dedup_key TEXT
);
CREATE TABLE formats (
    item TEXT NOT NULL REFERENCES items(id),
    name TEXT NOT NULL,
    inline BLOB,
    blob TEXT,
    PRIMARY KEY(item, name)
);
CREATE INDEX items_order ON items(pinned DESC, touched DESC, id ASC);
CREATE INDEX items_created ON items(created);
CREATE INDEX items_group ON items(group_id);
CREATE INDEX items_thumbnail ON items(thumbnail);
CREATE INDEX items_preview ON items(preview);
CREATE INDEX items_dedup_key ON items(dedup_key);
CREATE INDEX formats_blob ON formats(blob);
CREATE INDEX items_touched ON items(touched DESC, id ASC);
CREATE INDEX items_expiry ON items(expires_at) WHERE expires_at IS NOT NULL;
CREATE INDEX items_retention ON items(used_at, touched)
    WHERE pinned=0 AND favorite=0 AND group_id IS NULL;
PRAGMA user_version = 3;
```

连接保留 `journal_mode=WAL`、`temp_store=MEMORY`、`secure_delete=ON`，新增 `foreign_keys=ON`。

## 升级流程与数据约定

1. 使用现有 SQLCipher 主密钥打开数据库，保留 M0 的错密钥诊断。读取 `user_version`；版本已是 3 时直接使用，高于当前支持版本时明确拒绝打开，不尝试降级。
2. 只有版本低于目标且存在 `items` 表时备份。升级阶段使用独占锁封住 checkpoint 与复制之间的并发写入窗口；执行 `PRAGMA wal_checkpoint(TRUNCATE)`，验证返回的 busy / WAL frame 状态。占用导致无法备份时终止升级。
3. 将加密 `history.db` 逐字节复制到 `history.db.bak-v<起始版本>`（v0、v1 或 v2），同步写入磁盘。通过 `create_new` 禁止覆盖；同名文件已存在时追加 `-<Unix毫秒>-<序号>`。只复制数据库；迁移不改写、不删除任何 blob。备份需要配合原 `key.bin` 和 `data/blobs` 使用。
4. 每个版本在独立事务内执行 DDL、旧记录回填与 `user_version` 更新，全部成功才提交。当前迁移为 v0 → v1 → v2 → v3；从已有版本继续执行后续迁移。新库也经过同一迁移链，但不生成无意义的空库备份。v2 新增可空 `dedup_key TEXT` 列和非唯一索引 `items_dedup_key`，并在该版本的事务内完成回填。v3 只新增四个查询索引，不改列、不回填数据；v2 升级前生成 `history.db.bak-v2`。
5. 迁移失败显式回滚，错误包含中文原因和备份位置。若底层 IO 连回滚状态也无法确认，会如实提示保留原库和备份，不宣称已经安全回滚。不会通过删除数据库或重建数据绕过错误。

`touched` 始终是递增排序计数。`created` / `used_at` 是 Unix 毫秒时间戳；旧数据两者统一设为本次迁移时刻。新记录二者设为保存时刻，重复复制和 `touch` 仅更新排序及 `used_at`，保留 `created` 和其他元数据。`touch` 仍不读取格式或 blob。

`size` 仅计全部原始格式字节，不计缩略图、预览图和数据库开销，也不按共享 blob 去重。旧内联格式使用 SQL `length(inline)`；仅 v0 → v1 迁移时，外部格式使用文件长度减去 `BLOB_OVERHEAD = 44`（标记 4 + nonce 24 + tag 16），缺失文件为 0，不为统计大小解密。该旧库只包含 CM01，固定开销估算不适用于 CM02；后续版本迁移不执行此回填，新保存的 size 直接取原始格式字节总和。只有提取搜索文本时才读取必要的文本/路径格式，读取或认证失败留空并继续迁移。

`search_text` 的文本最多 16 KiB（UTF-8 边界截断）；文件记录保留文件名和完整路径；图片为空；富文本使用已有 `CF_UNICODETEXT`，不额外解析 HTML/RTF 或抓取远程资源。为兼容 M0，带纯文本的混合富文本仍分类为 `text`，仅含 HTML/RTF 的记录为 `rich`。

独立列是权威数据。持久化 `view` JSON 仅保留 id、summary、formats、placeholder、files 等展示字段，读取时使用列值组装 `ItemView`。新增展示字段均支持 serde 默认值。搜索文本只留在数据库，不进入列表响应/快速面板缓存，避免每条额外传输最长 16 KiB。`thumb://` 仍校验哈希且只能读取已登记在 `thumbnail` / `preview` 列中的对象。

## 文件去重键与自写回检测

`Clip::hash()` 仍表示全部原始格式的内容身份，新记录 `id` 继续使用它。新增纯函数 `Clip::dedup_key()`：可解码出非空路径集合的 `CF_HDROP` 记录，将路径分隔符统一为 `\`、去掉末尾分隔符、转小写，再排序并去重。键原文为 `files:<剪切标志 0/1>:<NUL 分隔的路径集合>`，最终取 SHA-256。`Preferred DropEffect` 的前四字节按小端读取，含 MOVE(2) 就是剪切（即使同时含 COPY/LINK）；缺失、不足四字节或不含 MOVE 均按复制。附加 DIB、DIBV5、HTML 不影响文件去重键。其他记录及损坏/空 HDROP 使用原 `hash()`。

v2 回填只查询 `formats` 内联的 `CF_HDROP` 和 `Preferred DropEffect`，不读取外部 blob。能计算文件键时回填文件键；非文件、路径无效/为空、格式载荷缺失或外置等不能计算的记录回填旧 `id`。缺少 DropEffect 格式按复制；存在格式行但载荷不可读则回退旧 `id`。迁移不合并、不删除已有重复记录，不改写 id、格式、排序或 blob；用户可在主窗口删除旧重复项。

保存路径先计算原始 hash 与文件去重键，再按 `dedup_key` / 旧 id 查找，多个命中取 `touched` 最大者（相同则按 id 稳定排序），只更新该行的 `touched` 和 `used_at`，保留首次保存的格式、预览和其他元数据。命中在生成缩略图和准备 blob 之前返回，不为 QQ 附加位图产生孤儿对象。未命中才生成并插入新记录及去重键。复制与剪切始终保留为不同记录。

自写回检测不依赖 `id == hash()`：runtime 调用 `clipboard::capture_pending`；采集先以 Win32 剪贴板序列号和 `SELF_SEQUENCE` 比较，打开后也可用本进程 `OWNER_MARKER` / `TOKEN` 确认自写回。因此本轮仅将 runtime 的采集保存调用切换为锁外准备入口，不改变采集调度、粘贴代号或修饰键逻辑，`Storage::touch` 仍只更新数据库，不读取 blob。

## 分页与图片规范化

- `Storage::list_page(&ListFilter, offset: usize, limit: usize)`；`ListFilter` 支持 `kind`、`favorite_only`、`group_id` 的组合等值过滤，参数绑定，单页上限 500。limit=0 返回空，超范围 offset 返回空；排序 `pinned DESC, touched DESC, id ASC`，id 只作为稳定兜底。
- `list_items(filter, offset, limit)` 在后台任务中直接查询 Storage。保留 `Storage::list()` 作为旧调用者的 200 条第一页兼容接口；runtime 明确查询第一页 200 条填充快速面板缓存。
- 主窗口每页 100 条，接近底部追加；重建已加载范围时按 id 保留选中项；新记录把选中项推入下一页时继续查找。请求代号隔离过期响应，失败保留现有内容并提供重试。详情保持原有代号保护。
- 采集成功后用纯函数移除与 CF_DIBV5 同时存在的 CF_DIB，再交给存储计算 hash；仅 DIB 时保留。写回不修改旧记录；仅 V5 时让 Windows 合成 DIB / BITMAP。缩略图及大预览均支持仅 V5，并有透明度回归测试。
- D-6 在采集规范化路径中处理，哈希算法本身不变。PNG 按 chunk 边界找到 IEND，DIB 支持常见 12/40/52/56/108/124 字节头、位深、压缩方式、外置/内置位域掩码、调色板和 DWORD 行对齐；保留声明的像素长度与 V5 尾部色彩配置数据。无效或不确定头、计算越界、截断内容都原样保留。

## T2 删除、孤儿扫描与保留策略

`Storage::delete(&[String]) -> Result<DeleteReport>` 在一个事务内收集候选 blob、删除 formats 和 items，提交后才回收文件。空列表、不存在的 id 均返回零；重复 id 只计实际删除的行。手工删除允许删除最新记录和受保护记录。候选哈希去重后分别检查 `formats.blob`、`items.thumbnail`、`items.preview`；三处均不再引用才删除文件。因此文件记录、位图记录、原始格式与缩略图之间共享同一哈希不会被误删。删除不加载或解密 blob，也不删除记录指向的源文件。

`DeleteReport` 返回 `deleted_items`、`reclaimed_blobs`、`failed_blobs`、`vacuumed`、`maintenance_errors`。文件不存在不算本次回收；文件被占用等失败留在磁盘，在 report 中记录，下一次启动扫描重试。提交后的维护错误不把已经完成的数据库删除返回成失败。命令 `delete_items` 在后台线程执行，仅允许主窗口调用，之后 `runtime::refresh` 更新 `state.items`、`hook::READY`、打开中的快速面板以及主窗口事件。空历史关闭快速面板并禁用 READY。刷新查询与缓存替换在同一 storage 锁范围内，避免并发刷新用旧快照覆盖新缓存。

启动入口在 `Storage::open`（含迁移）成功后、runtime 启动前调用 `scan_orphan_blobs()`。它仅遍历 `data/blobs` 的直接普通文件，删除 `*.tmp` 以及三处均未引用的 64 位小写十六进制文件；不递归、不跟随符号链接，不碰大写哈希、其他文件名或目录。迁移函数本身仍不删除 blob，但迁移之后的扫描可能回收历史孤儿。独立使用 Storage 的调用者需显式调用扫描，`open` 本身不隐含文件回收。

**备份风险：`history.db.bak-v*` 不是完整数据备份。恢复旧库后，旧库引用的 blob 可能已被后来的删除、自动清理或启动扫描回收。需要可恢复备份时，应在应用退出后同时保留数据库、`key.bin` 和完整 `data/blobs`；不要只恢复旧数据库覆盖当前工作库。**

`RetentionPolicy` 默认 1000 条、1 GiB（1073741824 字节）、30 天。`validate_retention_policy` 是纯函数：条数和空间必须大于零，空间不超过 `i64::MAX`，只有 `max_days=0` 表示不限天数。runtime 保存 `Mutex<RetentionPolicy>`，供 T3 替换；T2 不读取 settings，不增加设置界面或环境变量覆盖。

`Storage::cleanup(&policy, now)` 的 now、used_at 和 expires_at 都使用 Unix 毫秒。筛选在 SQL CTE / 窗口函数中完成，只把待删除 id 传入共用的 delete 路径：

1. 全局 `touched` 最大的一条始终保留；并列按 id 升序选择一条，**即使到期、超过天数或单条超出容量也保留**。该规则不限制手工删除。
2. 其他 `expires_at <= now` 的记录到期删除，**不受 pinned、favorite、group_id 保护**。T7 可复用此入口；T2 尚无后台到期定时器或敏感规则。
3. 普通策略只考虑 `pinned=0 AND favorite=0 AND group_id IS NULL` 的记录。受保护记录不删除，也完全不计条数和空间。天数依据 `used_at < now - max_days * 86400000`，恰好到边界仍保留；created 不参与判断。
4. 先排除到期/过旧的必删项，再对普通剩余项从新到旧累计条数和 size，删除超限的旧前缀，最终按 touched 从旧到新执行。条数/空间恰好等于上限不删除；size 使用原始格式字节列，不按 blob 去重，不包含预览、数据库和受保护记录，因此不是物理磁盘空间上限。

## T2 调度、VACUUM 与并发影响

- runtime 开始监听前先按默认策略清理一次，再加载初始缓存；若本次大量删除已经成功 VACUUM，不重复整理。
- `Storage::save` 保持原接口；`save_with_outcome` 沿用完全相同的去重逻辑，只额外返回是否新插入。worker 仅在新插入后累计计数，以单调时钟判断“距离上次清理至少 30 秒，或新增达到 20 条”；去重命中和 touch 都不触发。失败也重置节流，避免故障期间每次采集都重试昂贵维护。保存与清理共用一次 refresh。
- 启动时 `freelist_count / page_count > 25%` 执行 VACUUM；单次 delete（包括 cleanup）实际删除 **超过 200 条** 时在事务提交后执行。200 条不触发，201 条触发。保持 WAL、SQLCipher 和 secure_delete=ON。错误记录诊断或 report，不影响已保存的记录。
- VACUUM 同步运行并持有 storage 锁。broker 和键盘钩子不持有该锁，UI 调用使用后台任务；采集保存、粘贴 load/touch、分页和图片读取仍可能等待，worker 后续采集也会延后。启动整理发生在监听前，会增加启动时间；运行期间整理可能使连续复制合并，只捕获随后可见的剪贴板内容。没有宣称零延迟或完整保存维护期间每次瞬时变化。
- 耗时取决于数据库、磁盘、剩余空间和竞争负载；默认节流及大批删除阈值减少整理频率，不提供耗时上限。可启用 `CLIPBOARD_M0_DIAG=1`，查看 `vacuum elapsed_ms=... ok=...`、`delete items=... blobs=... failed_blobs=...` 和 `orphan_scan blobs=... temps=... failed=...`。本轮只验证小型隔离数据，未做 1 GiB 数据库或高负载延迟基准。
- 文件回收和数据库提交不是跨介质事务；崩溃后可能留孤儿，启动扫描修复。所有在线存储操作依赖本进程的 storage 锁；不要让多个实例同时使用同一数据目录，T2 未引入跨进程 blob 写入/回收锁。

## blob 瘦身 A / B：CM02 与锁外准备（2026-11-10）

数据库版本仍为 v3，不迁移或重压已有对象。CM01 与 CM02 在同一 blobs 目录共存，文件名继续是明文 SHA-256；已有同哈希文件不覆盖。删除与孤儿扫描只依据引用和文件名，不区分对象版本。

| 对象 | 字节布局 | AAD |
|---|---|---|
| CM01 | `CM01` 标记 4 + nonce 24 + 原文密文 N + tag 16 | id 的 UTF-8 字节（与旧实现相同） |
| CM02 | `CM02` 标记 4 + 明文长度 u64 LE 8 + nonce 24 + zstd 密文 N + tag 16 | UTF-8 的 `CM02:` + id，再追加同一 8 字节明文长度 |

两种格式均使用现有 HKDF 派生密钥和 XChaCha20-Poly1305 随机 nonce。CM02 先认证再解压；版本与长度受 AAD 保护，修改版本无法作为 CM01 通过认证。声明长度不得超过与采集共用的 128 MiB 上限，zstd bulk 解压的输出容量严格限制为声明长度，实际长度还必须一致。长度、格式、解密或解压失败均返回错误。

压缩策略为纯函数：PNG 签名的内容（包括原 PNG、缩略图和预览）直接跳过；其他外置载荷使用 zstd 级别 3。仅在 `(压缩字节数 + CM02 额外的 8 字节) × 100 < 明文字节数 × 95` 时采用 CM02，否则使用 CM01。小文本等内联格式仍由 SQLCipher 保护，不经过 blob 压缩。

runtime 改用 `Storage::save_shared(&Mutex<Storage>, &Clip)`：先在锁外计算身份，锁内提前查重；未命中时复制 Zeroizing 密钥，在锁外生成预览、压缩与加密，只保存在内存。提交时重新持锁查重，避免并发插入覆盖首次记录；再写临时文件、rename 并提交数据库。已有对象不覆写，也不在锁外依赖“文件存在”的快照，因此准备期间发生删除/扫描仍能安全落盘。旧 `save` / `save_with_outcome` 接口保留供独占存储调用者使用。`Storage::touch` 不变。

准备期间没有未登记的落盘对象，孤儿扫描不会误删待提交文件；提交失败遗留的对象仍由既有启动扫描回收。锁外准备增加暂存密文的内存占用；准备阶段同时持有原始格式和已准备的密文，压缩期间还会暂存压缩缓冲区。采集与粘贴仍共用一个串行 worker，锁外处理并不等于粘贴可抢占正在进行的采集；它减少的是分页、预览等其他调用者的锁等待。文件写入、数据库提交、load、清理仍持锁。

人工跨应用粘贴、实际磁盘缩减和主观延迟按 M1 人工验收清单执行；自动化通过不代表画图、Word、QQ、微信已经人工验收。

## D / E：图片编码与 CM03 对象（2026-11-10）

采用独立 CM03 而非修改 CM02：旧 CM02 的解压明文语义保持不变，新算法有独立认证域，旧程序遇到 CM03 会明确拒绝。数据库版本仍为 v3，文件名仍是原文 SHA-256，size 仍是原始格式字节合计，不迁移、不重写旧对象。CM01/CM02/CM03 共存；删除与孤儿扫描按引用回收，不依赖对象内容或版本。

### CM03 二进制布局

| 偏移 / 长度 | 内容 |
|---|---|
| 0 / 4 | ASCII `CM03` |
| 4 / 8 | 原始明文长度 N，u64 little-endian |
| 12 / 24 | XChaCha20 随机 nonce |
| 36 / 可变 | zstd 流的加密密文 |
| 末尾 / 16 | Poly1305 tag |

AAD 为 ASCII `CM03:` + id 的 UTF-8 字节 + 头中完全相同的 8 字节长度。HKDF、主密钥与 AEAD 算法沿用既有实现；版本、长度及身份受认证保护，CM03 改成 CM02 或 CM01（包括去掉 8 字节以对齐 nonce）无法通过认证。

zstd 解压后的格式为 `[预测后的 DIB，长度 N][全局滤波类型，1 字节]`。当前唯一允许类型是 `0x02`（PNG Up），应用于每一行；其它字节均拒绝。固定 Up 无需为每行保存相同类型，额外开销仅 1 字节；该字节与数据一起压缩、加密、认证。PNG 同名滤波只描述预测算法，这个流不是 PNG 文件。

先认证，再以严格 `N + 1` 容量执行 bulk 解压，要求实际长度完全相等；再弹出并验证滤波类型，复用 DIB 解析器校验原文结构与所有范围后逆变换。`N + 1 <= 128 MiB`；恰好 128 MiB 的原文不尝试 CM03，仍可按原有 CM02/CM01 策略保存。篡改长度、认证正确但结构损坏、截断、输出比声明值大或小均返回错误，不分配无限输出。CM01 读取保持既有兼容行为。

### DIB 预测范围与纯函数选择

`image_normalize::parse_dib` 为规范化及预测共用的头部解析器。规范化沿用原有允许范围，不改变采集截断或身份规则；预测入口支持 12/40/52/56/108/124 字节头中的 24/32 位 BI_RGB、BI_BITFIELDS，其中 12 字节 core 头仅 24 位无压缩。24 位 BI_BITFIELDS 只在预测入口扩展，掩码必须在位深内、非零、不重叠且连续；不支持压缩方式、无效/不确定/截断结构均回退。

步长 `stride = ((width * bpp + 31) / 32) * 4`，像素行字节数 `width * (bpp / 8)`。保留原有内存行顺序，正负高度均不翻转。每行的像素字节执行 `filtered = raw.wrapping_sub(previous_row)`；首行上方视为零，故首行不变；逆变换为 wrapping_add。行末 padding 不预测但跟随流完整保存。头部、内/外置掩码、调色板、声明尺寸超出真实像素的额外区、ICC 与任意尾部全部原样保存。

`crypto::select_payload` 为纯函数：先计算原 CM02 候选（zstd 3），再对可识别 DIB 预测压缩。CM03/CM02 加密开销同为 52 字节；CM03 压缩流必须严格小于 CM02，且 `(压缩长度 + 8) × 100 < N × 95` 才使用。否则回退原 CM02/CM01。PNG 魔数 `89 50 4E 47 0D 0A 1A 0A` 和 JPEG 魔数 `FF D8 FF` 均跳过压缩，使用 CM01。高噪点或纯色已接近压缩极限的样本允许回退，不为了使用新版本而增加大小。

`PreparedSave` 仍在锁外完成预览、预测、压缩和认证加密；提交保持既有锁内复查、写入及事务。未修改 touch、dedup_key、自写回检测或按键规则。双路尝试会同时持有原文、CM02 候选、预测缓冲和 CM03 候选，峰值内存和保存 CPU 成本增加；worker 串行的排队限制仍在。

### 预览编码与访问

缩略图/大预览缩放前检测源图 alpha（保留高位深判断，避免缩放舍入误选 JPEG）；全不透明时转 RGB8，比较 JPEG 85 和 Best/Adaptive PNG，取更小；透明时使用 RGBA8 Best/Adaptive PNG，已有透明预览与逐字节 RGBA 测试继续通过。内部 `Preview.png` / `large_png` 字段名保留兼容调用者，内容依签名识别。`thumb://` 仍只接受 GET、有效哈希及 thumbnail/preview 列登记的对象，通过白名单后按魔数返回 MIME；不认识的内容返回 404 和空体，响应保留 nosniff/no-store。旧 PNG 不重新编码，前端无需更改。

原始 JPG 等有损格式解码后的像素无损保存通常大于原 JPG；JPEG 展示副本不改变原始格式载荷。真实图片的压缩收益、预览清晰度及画图/Word/QQ/微信粘贴仍按人工清单验证。

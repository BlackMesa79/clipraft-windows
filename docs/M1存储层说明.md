# M1 / T1–T7 存储层说明

更新日期：2026-11-12。当前 `PRAGMA user_version = 4`。

## 最终 schema

以下是版本 4 的等价建表语句（FTS 自动生成的内部表不展开）。实现采用事务内创建 v0 表后逐版迁移，新库与 M0 旧库升级后的 schema 已通过一致性测试。

```sql
CREATE TABLE groups (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    sort INTEGER NOT NULL,
    created INTEGER NOT NULL
);
CREATE TABLE settings (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);
CREATE TABLE items (
    id TEXT PRIMARY KEY,
    view TEXT NOT NULL,
    touched INTEGER NOT NULL,
    kind TEXT NOT NULL DEFAULT 'text',
    created INTEGER NOT NULL DEFAULT 0,
    used_at INTEGER NOT NULL DEFAULT 0,
    size INTEGER NOT NULL DEFAULT 0,
    pinned INTEGER NOT NULL DEFAULT 0,
    favorite INTEGER NOT NULL DEFAULT 0,
    group_id INTEGER REFERENCES groups(id),
    source_exe TEXT,
    source_title TEXT,
    sensitive INTEGER NOT NULL DEFAULT 0,
    expires_at INTEGER,
    search_text TEXT NOT NULL DEFAULT '',
    thumbnail TEXT,
    preview TEXT,
    dedup_key TEXT,
    search_pinyin TEXT NOT NULL DEFAULT '',
    is_link INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE formats (
    item TEXT NOT NULL REFERENCES items(id),
    name TEXT NOT NULL,
    inline BLOB,
    blob TEXT,
    PRIMARY KEY(item, name)
);
CREATE INDEX items_order ON items(pinned DESC, touched DESC, id ASC);
CREATE INDEX items_created ON items(created);
CREATE INDEX items_group ON items(group_id);
CREATE INDEX items_thumbnail ON items(thumbnail);
CREATE INDEX items_preview ON items(preview);
CREATE INDEX items_dedup_key ON items(dedup_key);
CREATE INDEX formats_blob ON formats(blob);
CREATE INDEX items_touched ON items(touched DESC, id ASC);
CREATE INDEX items_expiry ON items(expires_at) WHERE expires_at IS NOT NULL;
CREATE INDEX items_retention ON items(used_at, touched)
    WHERE pinned=0 AND favorite=0 AND group_id IS NULL;
CREATE INDEX items_link ON items(is_link, pinned DESC, touched DESC, id ASC);
CREATE TABLE items_fts_map (
    search_id INTEGER PRIMARY KEY,
    item_id TEXT NOT NULL UNIQUE REFERENCES items(id)
);
CREATE VIRTUAL TABLE items_fts USING fts5(
    search_text, search_pinyin, tokenize='trigram'
);
CREATE TRIGGER items_search_insert AFTER INSERT ON items BEGIN
    INSERT INTO items_fts_map(item_id) VALUES(new.id);
    INSERT INTO items_fts(rowid,search_text,search_pinyin)
        SELECT search_id,new.search_text,new.search_pinyin FROM items_fts_map WHERE item_id=new.id;
END;
CREATE TRIGGER items_search_delete BEFORE DELETE ON items BEGIN
    DELETE FROM items_fts WHERE rowid=(SELECT search_id FROM items_fts_map WHERE item_id=old.id);
    DELETE FROM items_fts_map WHERE item_id=old.id;
END;
CREATE TRIGGER items_search_update AFTER UPDATE OF search_text,search_pinyin ON items BEGIN
    UPDATE items_fts SET search_text=new.search_text,search_pinyin=new.search_pinyin
        WHERE rowid=(SELECT search_id FROM items_fts_map WHERE item_id=new.id);
END;
PRAGMA user_version = 4;
```

连接保留 `journal_mode=WAL`、`temp_store=MEMORY`、`secure_delete=ON`，新增 `foreign_keys=ON`。

## 升级流程与数据约定

1. 使用现有 SQLCipher 主密钥打开数据库，保留 M0 的错密钥诊断。读取 `user_version`；版本已是 4 时直接使用，高于当前支持版本时明确拒绝打开，不尝试降级。
2. 只有版本低于目标且存在 `items` 表时备份。升级阶段使用独占锁封住 checkpoint 与复制之间的并发写入窗口；执行 `PRAGMA wal_checkpoint(TRUNCATE)`，验证返回的 busy / WAL frame 状态。占用导致无法备份时终止升级。
3. 将加密 `history.db` 逐字节复制到 `history.db.bak-v<起始版本>`（v0、v1、v2 或 v3），同步写入磁盘。通过 `create_new` 禁止覆盖；同名文件已存在时追加 `-<Unix毫秒>-<序号>`。只复制数据库；迁移不改写、不删除任何 blob。备份需要配合原 `key.bin` 和 `data/blobs` 使用。
4. 每个版本在独立事务内执行 DDL、旧记录回填与 `user_version` 更新，全部成功才提交。当前迁移为 v0 → v1 → v2 → v3 → v4；从已有版本继续执行后续迁移。新库也经过同一迁移链，但不生成无意义的空库备份。v2 新增可空 `dedup_key TEXT` 列和非唯一索引 `items_dedup_key`，并在该版本的事务内完成回填。v3 只新增四个查询索引，不改列、不回填数据；v2 升级前生成 `history.db.bak-v2`。v4 新增搜索派生列、FTS 和映射表及触发器，在同一事务内回填并执行 FTS `integrity-check`；v3 升级前生成 `history.db.bak-v3`。
5. 迁移失败显式回滚，错误包含中文原因和备份位置。若底层 IO 连回滚状态也无法确认，会如实提示保留原库和备份，不宣称已经安全回滚。不会通过删除数据库或重建数据绕过错误。

`touched` 始终是递增排序计数。`created` / `used_at` 是 Unix 毫秒时间戳；旧数据两者统一设为本次迁移时刻。新记录二者设为保存时刻，重复复制更新排序及 `used_at`，T6 采集入口同时替换最近来源；`touch` 仅更新排序及 `used_at`。两者均保留 `created` 和其他元数据。`touch` 仍不读取格式或 blob。

`size` 仅计全部原始格式字节，不计缩略图、预览图和数据库开销，也不按共享 blob 去重。旧内联格式使用 SQL `length(inline)`；仅 v0 → v1 迁移时，外部格式使用文件长度减去 `BLOB_OVERHEAD = 44`（标记 4 + nonce 24 + tag 16），缺失文件为 0，不为统计大小解密。该旧库只包含 CM01，固定开销估算不适用于 CM02；后续版本迁移不执行此回填，新保存的 size 直接取原始格式字节总和。只有提取搜索文本时才读取必要的文本/路径格式，读取或认证失败留空并继续迁移。

`search_text` 的文本最多 16 KiB（UTF-8 边界截断）；文件记录保留文件名和完整路径；图片为空；富文本使用已有 `CF_UNICODETEXT`，不额外解析 HTML/RTF 或抓取远程资源。为兼容 M0，带纯文本的混合富文本仍分类为 `text`，仅含 HTML/RTF 的记录为 `rich`。

独立列是权威数据。持久化 `view` JSON 仅保留 id、summary、formats、placeholder、files 等展示字段，读取时使用列值组装 `ItemView`。新增展示字段均支持 serde 默认值。搜索文本只留在数据库，不进入列表响应/快速面板缓存，避免每条额外传输最长 16 KiB。`thumb://` 仍校验哈希且只能读取已登记在 `thumbnail` / `preview` 列中的对象。

## 文件去重键与自写回检测

`Clip::hash()` 仍表示全部原始格式的内容身份，新记录 `id` 继续使用它。新增纯函数 `Clip::dedup_key()`：可解码出非空路径集合的 `CF_HDROP` 记录，将路径分隔符统一为 `\`、去掉末尾分隔符、转小写，再排序并去重。键原文为 `files:<剪切标志 0/1>:<NUL 分隔的路径集合>`，最终取 SHA-256。`Preferred DropEffect` 的前四字节按小端读取，含 MOVE(2) 就是剪切（即使同时含 COPY/LINK）；缺失、不足四字节或不含 MOVE 均按复制。附加 DIB、DIBV5、HTML 不影响文件去重键。其他记录及损坏/空 HDROP 使用原 `hash()`。

v2 回填只查询 `formats` 内联的 `CF_HDROP` 和 `Preferred DropEffect`，不读取外部 blob。能计算文件键时回填文件键；非文件、路径无效/为空、格式载荷缺失或外置等不能计算的记录回填旧 `id`。缺少 DropEffect 格式按复制；存在格式行但载荷不可读则回退旧 `id`。迁移不合并、不删除已有重复记录，不改写 id、格式、排序或 blob；用户可在主窗口删除旧重复项。

保存路径先计算原始 hash 与文件去重键，再按 `dedup_key` / 旧 id 查找，多个命中取 `touched` 最大者（相同则按 id 稳定排序），更新该行的 `touched` 和 `used_at`（T6 采集入口同时更新来源），保留首次保存的格式、预览和其他元数据。命中在生成缩略图和准备 blob 之前返回，不为 QQ 附加位图产生孤儿对象。未命中才生成并插入新记录及去重键。复制与剪切始终保留为不同记录。

自写回检测不依赖 `id == hash()`：runtime 调用 `clipboard::capture_pending`；采集先以 Win32 剪贴板序列号和 `SELF_SEQUENCE` 比较，打开后也可用本进程 `OWNER_MARKER` / `TOKEN` 确认自写回。因此本轮仅将 runtime 的采集保存调用切换为锁外准备入口，不改变采集调度、粘贴代号或修饰键逻辑，`Storage::touch` 仍只更新数据库，不读取 blob。

## 分页与图片规范化

- `Storage::list_page(&ListFilter, offset: usize, limit: usize)`；`ListFilter` 支持 `kind`、`favorite_only`、`group_id` 的组合等值过滤，参数绑定，单页上限 500。limit=0 返回空，超范围 offset 返回空；排序 `pinned DESC, touched DESC, id ASC`，id 只作为稳定兜底。
- `list_items(filter, offset, limit)` 在后台任务中直接查询 Storage。保留 `Storage::list()` 作为旧调用者的 200 条第一页兼容接口；runtime 明确查询第一页 200 条填充快速面板缓存。
- 主窗口每页 100 条，接近底部追加；重建已加载范围时按 id 保留选中项；新记录把选中项推入下一页时继续查找。请求代号隔离过期响应，失败保留现有内容并提供重试。详情保持原有代号保护。
- 采集成功后用纯函数移除与 CF_DIBV5 同时存在的 CF_DIB，再交给存储计算 hash；仅 DIB 时保留。写回不修改旧记录；仅 V5 时让 Windows 合成 DIB / BITMAP。缩略图及大预览均支持仅 V5，并有透明度回归测试。
- D-6 在采集规范化路径中处理，哈希算法本身不变。PNG 按 chunk 边界找到 IEND，DIB 支持常见 12/40/52/56/108/124 字节头、位深、压缩方式、外置/内置位域掩码、调色板和 DWORD 行对齐；保留声明的像素长度与 V5 尾部色彩配置数据。无效或不确定头、计算越界、截断内容都原样保留。

## T2 删除、孤儿扫描与保留策略

`Storage::delete(&[String]) -> Result<DeleteReport>` 在一个事务内收集候选 blob、删除 formats 和 items，提交后才回收文件。空列表、不存在的 id 均返回零；重复 id 只计实际删除的行。手工删除允许删除最新记录和受保护记录。候选哈希去重后分别检查 `formats.blob`、`items.thumbnail`、`items.preview`；三处均不再引用才删除文件。因此文件记录、位图记录、原始格式与缩略图之间共享同一哈希不会被误删。删除不加载或解密 blob，也不删除记录指向的源文件。

`DeleteReport` 返回 `deleted_items`、`reclaimed_blobs`、`failed_blobs`、`vacuumed`、`maintenance_errors`。文件不存在不算本次回收；文件被占用等失败留在磁盘，在 report 中记录，下一次启动扫描重试。提交后的维护错误不把已经完成的数据库删除返回成失败。命令 `delete_items` 在后台线程执行，仅允许主窗口调用，之后 `runtime::refresh` 更新 `state.items`、`hook::READY`、打开中的快速面板以及主窗口事件。空历史关闭快速面板并禁用 READY。刷新查询与缓存替换在同一 storage 锁范围内，避免并发刷新用旧快照覆盖新缓存。

启动入口在 `Storage::open`（含迁移）成功后、runtime 启动前调用 `scan_orphan_blobs()`。它仅遍历 `data/blobs` 的直接普通文件，删除 `*.tmp` 以及三处均未引用的 64 位小写十六进制文件；不递归、不跟随符号链接，不碰大写哈希、其他文件名或目录。迁移函数本身仍不删除 blob，但迁移之后的扫描可能回收历史孤儿。独立使用 Storage 的调用者需显式调用扫描，`open` 本身不隐含文件回收。

**备份风险：`history.db.bak-v*` 不是完整数据备份。恢复旧库后，旧库引用的 blob 可能已被后来的删除、自动清理或启动扫描回收。需要可恢复备份时，应在应用退出后同时保留数据库、`key.bin` 和完整 `data/blobs`；不要只恢复旧数据库覆盖当前工作库。**

`RetentionPolicy` 默认 1000 条、1 GiB（1073741824 字节）、30 天。`validate_retention_policy` 是纯函数：条数和空间必须大于零，空间不超过 `i64::MAX`，只有 `max_days=0` 表示不限天数。runtime 保存 `Mutex<RetentionPolicy>`，供 T3 替换；T2 不读取 settings，不增加设置界面或环境变量覆盖。

`Storage::cleanup(&policy, now)` 的 now、used_at 和 expires_at 都使用 Unix 毫秒。筛选在 SQL CTE / 窗口函数中完成，只把待删除 id 传入共用的 delete 路径：

1. 全局 `touched` 最大的一条在普通天数/容量策略中保留；并列按 id 升序选择一条。T7 起显式到期不再豁免 newest。该规则不限制手工删除。
2. `expires_at <= now` 的记录到期删除，**包含 newest，且不受 pinned、favorite、group_id 保护**。T7 已增加独立后台到期定时器，详见文末。
3. 普通策略只考虑 `pinned=0 AND favorite=0 AND group_id IS NULL` 的记录。受保护记录不删除，也完全不计条数和空间。天数依据 `used_at < now - max_days * 86400000`，恰好到边界仍保留；created 不参与判断。
4. 先排除到期/过旧的必删项，再对普通剩余项从新到旧累计条数和 size，删除超限的旧前缀，最终按 touched 从旧到新执行。条数/空间恰好等于上限不删除；size 使用原始格式字节列，不按 blob 去重，不包含预览、数据库和受保护记录，因此不是物理磁盘空间上限。

## T2 调度、VACUUM 与并发影响

- runtime 开始监听前先按默认策略清理一次，再加载初始缓存；若本次大量删除已经成功 VACUUM，不重复整理。
- `Storage::save` 保持原接口；`save_with_outcome` 沿用完全相同的去重逻辑，只额外返回是否新插入。worker 仅在新插入后累计计数，以单调时钟判断“距离上次清理至少 30 秒，或新增达到 20 条”；去重命中和 touch 都不触发。失败也重置节流，避免故障期间每次采集都重试昂贵维护。保存与清理共用一次 refresh。
- 启动时 `freelist_count / page_count > 25%` 执行 VACUUM；单次 delete（包括 cleanup）实际删除 **超过 200 条** 时在事务提交后执行。200 条不触发，201 条触发。保持 WAL、SQLCipher 和 secure_delete=ON。错误记录诊断或 report，不影响已保存的记录。
- VACUUM 同步运行并持有 storage 锁。broker 和键盘钩子不持有该锁，UI 调用使用后台任务；采集保存、粘贴 load/touch、分页和图片读取仍可能等待，worker 后续采集也会延后。启动整理发生在监听前，会增加启动时间；运行期间整理可能使连续复制合并，只捕获随后可见的剪贴板内容。没有宣称零延迟或完整保存维护期间每次瞬时变化。
- 耗时取决于数据库、磁盘、剩余空间和竞争负载；默认节流及大批删除阈值减少整理频率，不提供耗时上限。可启用 `CLIPBOARD_M0_DIAG=1`，查看 `vacuum elapsed_ms=... ok=...`、`delete items=... blobs=... failed_blobs=...` 和 `orphan_scan blobs=... temps=... failed=...`。本轮只验证小型隔离数据，未做 1 GiB 数据库或高负载延迟基准。
- 文件回收和数据库提交不是跨介质事务；崩溃后可能留孤儿，启动扫描修复。所有在线存储操作依赖本进程的 storage 锁；不要让多个实例同时使用同一数据目录，T2 未引入跨进程 blob 写入/回收锁。

## blob 瘦身 A / B：CM02 与锁外准备（2026-11-10）

数据库版本仍为 v3，不迁移或重压已有对象。CM01 与 CM02 在同一 blobs 目录共存，文件名继续是明文 SHA-256；已有同哈希文件不覆盖。删除与孤儿扫描只依据引用和文件名，不区分对象版本。

| 对象 | 字节布局 | AAD |
|---|---|---|
| CM01 | `CM01` 标记 4 + nonce 24 + 原文密文 N + tag 16 | id 的 UTF-8 字节（与旧实现相同） |
| CM02 | `CM02` 标记 4 + 明文长度 u64 LE 8 + nonce 24 + zstd 密文 N + tag 16 | UTF-8 的 `CM02:` + id，再追加同一 8 字节明文长度 |

两种格式均使用现有 HKDF 派生密钥和 XChaCha20-Poly1305 随机 nonce。CM02 先认证再解压；版本与长度受 AAD 保护，修改版本无法作为 CM01 通过认证。声明长度不得超过与采集共用的 512 MiB 上限，zstd bulk 解压的输出容量严格限制为声明长度，实际长度还必须一致。长度、格式、解密或解压失败均返回错误。

压缩策略为纯函数：PNG 签名的内容（包括原 PNG、缩略图和预览）直接跳过；其他外置载荷使用 zstd 级别 3。仅在 `(压缩字节数 + CM02 额外的 8 字节) × 100 < 明文字节数 × 95` 时采用 CM02，否则使用 CM01。小文本等内联格式仍由 SQLCipher 保护，不经过 blob 压缩。

runtime 改用 `Storage::save_shared(&Mutex<Storage>, &Clip)`：先在锁外计算身份，锁内提前查重；未命中时复制 Zeroizing 密钥，在锁外生成预览、压缩与加密，只保存在内存。提交时重新持锁查重，避免并发插入覆盖首次记录；再写临时文件、rename 并提交数据库。已有对象不覆写，也不在锁外依赖“文件存在”的快照，因此准备期间发生删除/扫描仍能安全落盘。旧 `save` / `save_with_outcome` 接口保留供独占存储调用者使用。`Storage::touch` 不变。

准备期间没有未登记的落盘对象，孤儿扫描不会误删待提交文件；提交失败遗留的对象仍由既有启动扫描回收。锁外准备增加暂存密文的内存占用；准备阶段同时持有原始格式和已准备的密文，压缩期间还会暂存压缩缓冲区。采集与粘贴仍共用一个串行 worker，锁外处理并不等于粘贴可抢占正在进行的采集；它减少的是分页、预览等其他调用者的锁等待。文件写入、数据库提交、load、清理仍持锁。

人工跨应用粘贴、实际磁盘缩减和主观延迟按 M1 人工验收清单执行；自动化通过不代表画图、Word、QQ、微信已经人工验收。

## D / E：图片编码与 CM03 对象（2026-11-10）

采用独立 CM03 而非修改 CM02：旧 CM02 的解压明文语义保持不变，新算法有独立认证域，旧程序遇到 CM03 会明确拒绝。数据库版本仍为 v3，文件名仍是原文 SHA-256，size 仍是原始格式字节合计，不迁移、不重写旧对象。CM01/CM02/CM03 共存；删除与孤儿扫描按引用回收，不依赖对象内容或版本。

### CM03 二进制布局

| 偏移 / 长度 | 内容 |
|---|---|
| 0 / 4 | ASCII `CM03` |
| 4 / 8 | 原始明文长度 N，u64 little-endian |
| 12 / 24 | XChaCha20 随机 nonce |
| 36 / 可变 | zstd 流的加密密文 |
| 末尾 / 16 | Poly1305 tag |

AAD 为 ASCII `CM03:` + id 的 UTF-8 字节 + 头中完全相同的 8 字节长度。HKDF、主密钥与 AEAD 算法沿用既有实现；版本、长度及身份受认证保护，CM03 改成 CM02 或 CM01（包括去掉 8 字节以对齐 nonce）无法通过认证。

zstd 解压后的格式为 `[预测后的 DIB，长度 N][全局滤波类型，1 字节]`。当前唯一允许类型是 `0x02`（PNG Up），应用于每一行；其它字节均拒绝。固定 Up 无需为每行保存相同类型，额外开销仅 1 字节；该字节与数据一起压缩、加密、认证。PNG 同名滤波只描述预测算法，这个流不是 PNG 文件。

先认证，再以严格 `N + 1` 容量执行 bulk 解压，要求实际长度完全相等；再弹出并验证滤波类型，复用 DIB 解析器校验原文结构与所有范围后逆变换。`N + 1 <= 512 MiB`；恰好 512 MiB 的原文不尝试 CM03，仍可按原有 CM02/CM01 策略保存。篡改长度、认证正确但结构损坏、截断、输出比声明值大或小均返回错误，不分配无限输出。CM01 读取保持既有兼容行为。

### DIB 预测范围与纯函数选择

`image_normalize::parse_dib` 为规范化及预测共用的头部解析器。规范化沿用原有允许范围，不改变采集截断或身份规则；预测入口支持 12/40/52/56/108/124 字节头中的 24/32 位 BI_RGB、BI_BITFIELDS，其中 12 字节 core 头仅 24 位无压缩。24 位 BI_BITFIELDS 只在预测入口扩展，掩码必须在位深内、非零、不重叠且连续；不支持压缩方式、无效/不确定/截断结构均回退。

步长 `stride = ((width * bpp + 31) / 32) * 4`，像素行字节数 `width * (bpp / 8)`。保留原有内存行顺序，正负高度均不翻转。每行的像素字节执行 `filtered = raw.wrapping_sub(previous_row)`；首行上方视为零，故首行不变；逆变换为 wrapping_add。行末 padding 不预测但跟随流完整保存。头部、内/外置掩码、调色板、声明尺寸超出真实像素的额外区、ICC 与任意尾部全部原样保存。

`crypto::select_payload` 为纯函数：64 MiB 以内先计算原 CM02 候选（zstd 3），再对可识别 DIB 预测压缩。超过 64 MiB 时先只尝试 CM03；预测不适用或收益不足时，释放预测及压缩候选后才回退 CM02/CM01，不再做 CM02 对比。CM03/CM02 加密开销同为 52 字节；64 MiB 以内 CM03 压缩流必须严格小于 CM02，所有尺寸均要求 `(压缩长度 + 8) × 100 < N × 95` 才使用。否则回退原 CM02/CM01。PNG 魔数 `89 50 4E 47 0D 0A 1A 0A` 和 JPEG 魔数 `FF D8 FF` 均跳过压缩，使用 CM01。高噪点或纯色已接近压缩极限的样本允许回退，不为了使用新版本而增加大小。

`PreparedSave` 仍在锁外完成预览、预测、压缩和认证加密；提交保持既有锁内复查、写入及事务。未修改 touch、dedup_key、自写回检测或按键规则。64 MiB 以内双路尝试会同时持有原文、CM02 候选、预测缓冲和 CM03 候选；大图不再同时构造 CM02 候选。加密直接在最终对象缓冲中原位完成，减少一份密文副本；worker 串行的排队限制仍在。

### 预览编码与访问

缩略图/大预览缩放前检测源图 alpha（保留高位深判断，避免缩放舍入误选 JPEG）；全不透明时转 RGB8，比较 JPEG 85 和 Best/Adaptive PNG，取更小；透明时使用 RGBA8 Best/Adaptive PNG，已有透明预览与逐字节 RGBA 测试继续通过。内部 `Preview.png` / `large_png` 字段名保留兼容调用者，内容依签名识别。`thumb://` 仍只接受 GET、有效哈希及 thumbnail/preview 列登记的对象，通过白名单后按魔数返回 MIME；不认识的内容返回 404 和空体，响应保留 nosniff/no-store。旧 PNG 不重新编码，前端无需更改。

原始 JPG 等有损格式解码后的像素无损保存通常大于原 JPG；JPEG 展示副本不改变原始格式载荷。真实图片的压缩收益、预览清晰度及画图/Word/QQ/微信粘贴仍按人工清单验证。

## 512 MiB 上限、降级与大图内存（2026-11-10）

单个对象与一次采集累计上限统一为 **512 MiB（536,870,912 字节）**，提示中的 MB 按 MiB 向上取整。`crypto::MAX_PLAIN_BYTES` 是共用来源，`clipboard::MAX_BYTES` 引用它；`read_raw_limited` 在 `GlobalSize` 后、`GlobalLock`/复制前按剩余预算拒绝。已成功取得 DIBV5 时，在读取回调之前跳过 CF_DIB，采集末尾去冗余 DIB 的规范化仍保留。DIBV5 超限则尝试 DIB；其他超限格式也逐项跳过，有文本等有效内容便保存。无有效内容才提示，例如“图片过大（约 600MB），超过 512MB 上限，未记录”。diag 仅记跳过的格式、字节数、预算与原因，不记录载荷。

CM02/CM03 在认证和解压分配之前检查头部声明长度，超过 512 MiB 立即拒绝；认证后仍严格限长解压并核对实际长度。CM03 另需一个滤波字节，因此原文恰好 512 MiB 时回退 CM02/CM01。超过 64 MiB 的可预测位图只先尝试 CM03，合格即使用，不再生成 CM02 比较候选；不能使用时释放候选后回退。加密直接在最终对象缓冲中完成，避免额外整份密文副本；保存借用原始 Clip，大图不走 `f.bytes.clone()`（该复制仅限至多 64 KiB 的内联数据）。

DIB 预览像素预算从 3200 万提高到 `512 MiB / 4`（约 1.34 亿像素），通用解码器 `max_alloc` 同步提高到 512 MiB；单边仍限 16384 像素，文件路径预览仍限 50 MiB。4835×7253 的 32 位图可正常生成 256×160 范围的缩略图和 800×800 范围的预览。仍采用完整解码，内存不足时可能失败；24 位等 BMP 解码路径还需补文件头的输入副本。JPEG 预览有损，原始 DIB 无损。

约 140MB 位图的内存预算：令原文 `N=140,273,144` 字节（133.77 MiB），压缩对象有效字节为 C。保存的主要缓冲区峰值约 `3N`（401.32 MiB）：原文、预测副本、zstd 最大输出容量；预览阶段约 `2N` 加小图，预测和预览不同时存活。粘贴先 load 再写 HGLOBAL，主要缓冲峰值为 `max(N+2C, 2N)`；本次两种样本均约 267.55 MiB。以上为缓冲区估算，另加 zstd/图像编解码器、数据库、分配器与应用基线；不含源应用、已有系统剪贴板、Windows 自动合成的 DIB/Bitmap、目标应用显示。512 MiB 上限不是进程内存上限，大图采集与粘贴仍可能在串行 worker 排队。

本机 dev 优化构建、单线程、4835×7253 合成 DIBV5，分别在独立测试进程单次测量：

|---|---|---|---|---|---|

## T4 搜索与拼音（2026-11-11）

FTS 选择**独立内容表 + 整数映射表**：items 的主键是 TEXT，隐式 rowid 不适合跨 VACUUM 作为外部内容索引的标识；现有维护会执行 VACUUM。items_fts_map.search_id 是显式 INTEGER PRIMARY KEY，VACUUM 后保持稳定，映射到不变的 items.id。FTS 自带内容副本会增加数据库体积，但避免修改 items 主键和重建 formats 外键，且不触及 dedup_key。索引、映射、派生列都位于同一 SQLCipher 加密库。

保存准备阶段在锁外生成 search_pinyin 和 is_link，提交时和原 search_text 一起插入。INSERT、BEFORE DELETE、UPDATE OF search_text/search_pinyin 触发器同步 FTS，删除、保留策略清理和事务回滚都走同一路径；去重命中只更新既有记录的顺序，不重写首次内容。未来若修改文本或 kind，调用者必须同时重新计算 search_pinyin/is_link；触发器只同步已计算字段，不调用 Rust 拼音函数。items.id 仍不可变。

v4 回填只读取已有 search_text 和 kind，不解密 blob；按 id 每批 128 行遍历，回填派生列后创建映射及 FTS 内容，再运行 INSERT INTO items_fts(items_fts) VALUES('integrity-check')。迁移框架原有逐版事务、独占备份、不覆盖同名备份、失败回滚均保留。测试除 FTS 自身 integrity-check 外，还逐行比较 items/FTS 两列、检查三表行数和外键；覆盖更新、去重、手动删除、preview_cleanup、cleanup、201 条删除触发 VACUUM、重开及迁移失败。新建库与 v0 升级库的完整 sqlite_master schema（包含触发器）一致。

search_pinyin 保存两行：无声调全拼和首字母。保留原文中的非汉字，以支持 Hello你好 → Hellonihao / Hellonh；处理前 2000 个可转换汉字，在第 2001 个处停止。无汉字时字段为空。输入本身受 search_text 的 16KiB 限制，因而体积有界；两个派生串可能比原文更长。多音字取 pinyin 0.10 默认读音，不做词组消歧、繁简转换或声调匹配。

is_link 仅对 kind=text 设置：trim 后必须以 http:// 或 https:// 开头（忽略大小写），不含空白/控制字符，并能通过现有 tauri::Url 解析且具有 host。不访问网络，不检查域名是否存在；URL 前后其他文字、ftp、空主机和中间空格都不算链接。

ListFilter 增加 query: Option<String>；空白查询不加任何搜索条件。按 Unicode 空白拆词，所有词 AND；单词至少 3 个 Unicode 字符时，将每个词包成 FTS 双引号字面量，内部双引号翻倍，再以参数绑定 MATCH；较短词分别匹配 search_text / search_pinyin 的 LIKE，并转义反斜杠、% 和 _。两种路径组合仍是 AND，单词可分别命中原文和拼音列。kind=text 包含 text/rich，kind=link 使用 is_link=1，其他类型维持精确过滤；favorite_only、group_id、pinned DESC/touched DESC/id ASC 和 offset/limit 上限保持原行为。list_items 原接口直接反序列化新增字段；Storage::list 默认过滤与快速面板缓存不变。

短 LIKE 查询可能扫描较多记录，Unicode 大小写折叠也与 trigram 不完全相同（英文大小写两条路径均支持）；不承诺语言学归一化。图片无搜索文本，不做 OCR；纯 HTML/RTF 且无 CF_UNICODETEXT 的记录可能无法按内容搜索。独立 FTS 需要额外数据库空间，迁移也需要备份、回填和索引构建的时间与空间。

主窗口搜索使用约 150ms 防抖，组合输入结束后提交；筛选改变时立即失效旧请求、从第一页重载并选中首条，旧分页或等待分页的方向键不会覆盖新选择。删除后按当前过滤条件重建已加载范围。空白查询等同全部，类型过滤仍有效；无结果显示“没有匹配的记录”。没有加入可选高亮。

主窗口成功 show 后发 main-shown，前端 nextTick 后只调用 HTMLInputElement.focus()；首次挂载与退出设置页也聚焦搜索框。保留现有原生焦点、掩码键、修饰键和粘贴代号流程。设置页开启时显示事件不夺走设置字段的焦点。

键盘规则：搜索框中 ↑/↓ 移动列表，Enter 粘贴，Shift+Enter 纯文本粘贴；非空搜索框 Delete 始终交给原生文本编辑（末尾也不删除记录），空框 Delete 才删除所选；搜索框 Ctrl+A 选择文字，列表 Ctrl+A 选择已加载记录。isComposing、组合输入状态或 keyCode=229 时不处理列表快捷键。Esc 依次由设置页、删除确认条、右键菜单优先消费，再清空非空搜索，搜索已空才隐藏；Esc 不清除类型筛选。

## T5 置顶、收藏与分组（2026-11-11）

schema 仍为 v4，无 v5 迁移。已有 pinned、favorite、group_id、groups 和 items_group 索引足够本轮使用。没有添加 SQLite NOCASE 唯一索引：NOCASE 仅覆盖 ASCII，应用使用 Rust `trim()` + `to_lowercase()` 统一比较 Unicode 名称，字符长度按 `chars().count()` 计算（不是 UTF-8 字节数，也不是视觉字素数）。不额外做 Unicode 规范化或多字符 case folding。所有创建/改名入口都在 `BEGIN IMMEDIATE` 事务中检查去空白后的 1–40 字符、重名和 100 组上限，阻止校验与写入之间的竞争；不支持绕过应用直接写 groups 表。

命令与存储方法：

- `set_pinned(ids, value)` / `set_favorite(ids, value)`：一个事务逐 id 绑定更新，返回实际变化条数；重复 id、相同状态和不存在的记录不计数。只修改对应列，不修改 touched、used_at 或 view JSON。读取继续从独立列覆盖 ItemView。
- `list_groups()`：返回 id、name、sort、count；LEFT JOIN 使空组也显示 0，按 sort/id 排序，count 不受列表搜索和类型影响。
- `create_group(name)` 返回新组；`rename_group(id, name)` 保持 id/sort/created 和记录归属，允许只变更自身大小写。非法名称、重名、超限、不存在的目标组均返回中文错误。
- `delete_group(id)` 在同一事务先 `UPDATE items SET group_id=NULL`，再删除 groups 行；记录、格式与 blob 保留，不产生悬空外键。第二步失败时第一步回滚。
- `move_to_group(ids, group_id)`：先验证目标组存在，再批量更新；null 表示移出组，返回实际改动数。不存在的目标组或中途失败不会部分写入。Tauri JS 参数是 `groupId`。
- 可选 `reorder_groups` 未实现；新建组的 sort 为当前最大 sort+1。

`ListFilter.group_id` 的 None 表示不限制分组；-1 表示 `group_id IS NULL`；正常组 id 表示等值匹配。-1 仅是列表过滤值，不会写入数据库；`move_to_group(..., Some(-1))` 因目标不存在而报错。favorite_only、group_id、query、kind 全部以 AND 组合，复用原搜索、offset/limit、置顶优先和 touched/id 排序逻辑。

所有修改命令仅主窗口可用，拒绝 smoke；后台任务完成事务后释放 storage 锁，再调用 `runtime::refresh`。快速缓存的启动和刷新统一走默认过滤的 `Storage::list()`，最多 200 条、置顶优先。成功提交后若刷新失败，会明确返回“修改已保存，但刷新失败”，不声称事务回滚。主窗口的记录修改流程会主动重读列表/组数，history-changed 事件同时保持其他刷新路径。

不修改手动删除/清理入口：手动删除可移除任何保护状态的记录；普通自动容量/天数策略不删除置顶、收藏、组内记录，也不计其条数和空间。已有显式 expires_at 分支的到期规则保持不变。新增测试证明刚移入组的记录立即被 preview_cleanup / cleanup 排除，删除组后记录仍在，`PRAGMA foreign_key_check` 为空；故障触发器验证删除组与批量修改的原子性。

验证：Rust 473 passed / 3 ignored（新增 19），fmt、clippy、前端构建通过；T5 离屏 12 项、T4 离屏原有 17 项通过。日志、界面限制与人工步骤见 README 和 M1 人工验收清单的 T5 部分。


## T6 来源元数据（2026-11-11）

继续使用 v4 的 `source_exe/source_title` 列，无新迁移。`save_capture` 将独立的 `CaptureSource` 传给 `Storage::save_shared_with_source`；复用 owner 查询但不改变 owner_flush 上下文或判定。锁内首次查重、锁外准备后的再次查重和新记录插入均写入来源，查重更新与 touched/used_at 在同一 SQL 语句内完成。来源未知时传 `Some(CaptureSource::default())`，将两列清空为 NULL；兼容的非采集入口传 None，保留旧来源。`touch` 和 owner_flush 跳过均不修改来源。

## T7 敏感内容识别（待人工验收）

schema 仍为 v4，不迁移。`sensitive` 为 `0`（未标记）、`1`（敏感）、`-1`（用户确认不敏感）；`ItemView.sensitive` 只在列值等于 1 时为 true。`expires_at` 使用 Unix 毫秒，`items_expiry` 索引保持不变。settings 新增强类型 bool `sensitive_high_entropy=false`，旧库缺少该键时按默认值读取，保存时写入；损坏类型按现有逐字段回退流程处理。

`view` JSON 的 summary 为脱敏后再截取的摘要，新增内部 `sensitive_hits` 数组（规则名、UTF-8 字节区间），不增加数据库列。该元数据不进入 ItemView 前端响应。分页与按 id 读取快速面板字段共用同一安全装配函数；敏感记录不返回文件路径、来源标题、缩略图或预览引用。详情使用保存的命中区间遮蔽后截断；没有元数据的旧敏感记录保守遮蔽。仅主窗口显式 `reveal_item` 可以获取原文详情，仍遵守详情长度上限。`thumb://` 拒绝敏感记录引用的对象和任何未登记为缩略图/预览的正文 blob。

## B-04：实现缺陷与修订

发现三条相互放大的路径：

1. 前端 window focus 无条件 loadDetail，并同步浮窗；普通 blur 也无条件清空详情。仅点击或拖动引起的宿主/WebView 焦点变化即可造成清空/重读观感。
2. 每次同步浮窗都先 hide，发布后用 Tauri show；位置刷新还会重复 set_size/set_position/show。缺少同一选中项去重，原生焦点回送后可能继续触发同步。
3. PreviewState::publish 原本在持有快照 Mutex 时执行窗口回调。Win32 API 可以同步回送事件，重入读取快照存在死锁风险。这是实现层明确不安全的锁范围，不能由离屏渲染验证代替原生事件审查。

修订：

- 同一选中 id/显隐状态不重复发起浮窗请求，历史变化显式使缓存失效。普通 focus 只在详情缺失且无请求进行时读取；普通 blur 保留非敏感详情，敏感原文仍立即清理。
- main-activated/main-deactivated 区分原生前台变化，并保留主窗显隐和敏感内容清理。重复 focus 不能推动重复预览请求。
- 内容切换只更新快照，不先隐藏原生窗口。浮窗显示/定位统一为 SetWindowPos，始终带 SWP_NOACTIVATE、SWP_NOOWNERZORDER、SWP_NOZORDER；可见且几何未变时完全不调用窗口 API。显隐采用一致的原生路径，不再调用浮窗 Tauri show。
- 状态锁仅保护快照与代号，外部回调/窗口操作移出锁范围。回调允许重入读取或清空快照，代号变化后不报告为当前发布。

以上为代码与自动化确认的缺陷及修订，不宣称已经重现并录制完整原生循环。用户原生复测仍是最终验收条件。
